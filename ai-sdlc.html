AI-SDLC Pipeline

模型提供候选，裁决权在系统。

自研并在运行的 AI 研发流水线，可现场演示，源码暂不公开。从一句话需求出发，经需求、方案、编码、验证与人审，在 GitHub 模式下交付到可合并的 PR。

为什么采用分阶段裁决

生成代码、选择证据和宣布成功，如果都交给同一个概率系统，就缺少独立的交付判据。因此没有采用“一个大 Agent 自由循环调工具”，而是给每个阶段统一的结构。

生成候选 → 确定性验证 → 裁决：通过、转人工或拒绝

模型可以提出方案和返工建议，系统负责验收、权限、预算与状态推进。这个选择适用于有明确交付检查的任务；没有确定性判据的探索任务，仍然可以采用开放式循环。

十阶段交付链

十个阶段均设有不依赖模型自述的确定性验收。检查通过的含义受各阶段能力边界限制，结构完整不等于需求或方案在语义上正确。

每阶段的主要产物与系统检查
阶段主要产物与检查
01 · 需求结构化验收条件与命名测试；检查字段、编号唯一性和测试映射，不保证需求没有编造。
02 · 方案文件、符号与改动计划；核验引用存在、保留验收映射，不保证方案本身正确。
03 · 编码候选补丁由系统应用；补丁可应用且真实测试通过，否则进入有界修复循环。
04 · 静态门执行语法、类型、密钥、危险写法与依赖检查。
05 · 充分性门检查验收条件是否有测试认领；覆盖率能力的现有限制见下方边界。
06 · 装配组装证据包，将代码版本、变更、策略版本及裁决、产物清单绑定到同一指纹。
07 · 人审批准绑定当前证据指纹与 PR 代码版本，变化后立即失效。
08 · CI人审通过后核验 GitHub 必过检查项；本地模式汇总本地门禁。
09 · 发布生成模拟的 staging / canary 计划；不执行真实部署。
10 · 复盘记录运行结果并回流台账；记录留存不等于复盘判断已经被独立验证。

五个关键机制

01 · 补丁与测试的有界修复循环

候选在独立工作目录中生成。托管模型只提交补丁文本，由系统验证和应用；补丁失败或测试未通过时，用压缩后的结构化反馈返工。后续版本都从本轮捕获的同一基线重做，避免在失败补丁上持续叠加。

02 · 返工触发下游证据级联失效

代码退回重写后，静态检查、覆盖率、证据包、人审和 CI 结论从变化点向下游全部作废。只重跑失败项会留下“旧证据盖在新代码上”的窗口；新代码必须重新获取对应证据。

03 · 按失败性质路由

瞬时故障退避重试，质量问题返工，缺信息或授权时暂停等待，人拒绝或预算耗尽时终止。CI 超时、限流和连接中断只重试 CI，因为这些故障没有提供需要修改代码的证据。每阶段有独立重试预算。

04 · 真实执行与隔离边界

测试由系统真实运行，Docker 路径使用非 root 用户、资源配额、执行超时，测试与扫描阶段断网，模型与 GitHub 凭证不进入沙箱。依赖安装步骤允许联网。环境可能降级为进程隔离，运行记录必须反映实际隔离级别，不能把降级路径说成容器隔离。

05 · 检查点与恢复校验

跨阶段状态结构化保存，阶段边界写入 SQLite。恢复时检查运行目录、仓库根、分支和代码版本与检查点是否一致；不一致即停止。恢复检查证明的是本机状态一致，无法单独证明外部副作用的状态。

信任边界与独立证据

  • 仓库代码与注释：作为待处理数据，不能改写系统指令。
  • 模型生成的补丁：作为候选，由系统控制验证与应用。
  • 模型生成的测试：在隔离环境中运行，但不能单独为同源代码作证。

模型如果误解了需求，代码与测试可能一起错误、一起通过。独立放行依据来自仓库存量测试、确定性静态检查、GitHub 必过项与人工评审。所有结论绑定同一份代码与证据指纹，避免混用不同版本的检查和审批。

上下文按阶段组织

需求阶段提供检索到的代码正文与行号；方案阶段提供符号索引；编码阶段再提供计划点名文件的正文。上下文有预算与截断标记。当前方案阶段取符号索引的前 200 条，尚未按相关性筛选，这是更大仓库场景的限制。

当前实现边界

自研并在运行，可现场演示；未对外商用。

统计于 2026.09.09：流水线核心 8,960 行、控制台后端 1,464 行，共 10,424 行 Python 源码。按物理行统计，含空行与注释，不含测试代码、示例、基准脚本和第三方依赖。

自动化测试共 201 条：Python 194 条（流水线 173 条、控制台后端 21 条），控制台前端 7 条；不重复计入子测试。上述数字只说明实现规模，无生产吞吐数据，也不能据此声称研发提效或商业效果。

  • 交付终态：GitHub 模式停在可合并状态，由仓库维护者决定合并；本地模式提供写回目标仓库的演示路径。发布阶段仅生成模拟计划。
  • 部署形态：当前使用单机运行器与 SQLite 检查点，尚未验证企业级长任务调度和生产吞吐。
  • 测试充分性：覆盖率基线当前未真实采集，缺少覆盖率依赖时可能走演示估算；未实现 mutation testing，不能声称已保证覆盖率不低于改动前。
  • 语义正确性：需求与方案检查主要保证结构、引用及映射；模型自评分仅用于触发澄清，未做概率校准，不是正确率。
  • 隔离与恢复：依赖安装仍有供应链风险；实际隔离级别需要核验，恢复校验不覆盖外部副作用。
  • 离线能力：无模型凭据时只提供特定分页场景的确定性演示，通用需求不会被伪装成已完成。

可现场演示的内容

  1. 跑通一条完整流水线，查看阶段轨迹、验证结果和可合并终态。
  2. 故意触发一次质量失败，观察门禁阻断、返工与下游证据失效。
  3. 核对审批与当前代码版本的绑定，说明为什么旧批准不能继续用于新代码。
