SQL Agent · 自然语言数据分析

NL2SQL / Schema Linking / SQL 执行治理

企业生产项目
01业务问题
运营与分析人员需要从数百张业务表中取数，常规需求要等待 1–3 天研发排期。自然语言查询需要同时解决业务口径匹配和数据库执行风险。
02我负责的范围
2024.05–2026.03，在 NTT DATA 带 5 人技术线共同交付两条生产线；本项目于 2025.10 首次上线。负责架构、检索上下文、数据库运行时、SQL 安全与上线质量。
03一个关键技术取舍
采用业务域分流 → 表、字段、业务文档、SQL 示例四路召回 → 列级 Schema Linking。否掉“把全表 Schema 直接塞给模型”：无关字段会稀释语义，并推高成本。增加检索复杂度前，用同一冻结集做消融验证。
04结果与口径
60% → 24% → 10%SQL Agent 离线消融的检索误拒率；同一批 60 条冻结评测集中的 50 条可回答问题。分别对应表级基线、补齐四路检索、加入业务域分流。

有效只读端到端成功率 约 86%。

展开执行安全与成本口径

五道执行闸：只读账号、单语句 SELECT、AST 校验、全表扫描保护、执行超时。约束固化在执行链路中，模型生成的 SQL 不能直接获得执行权。

SQL Agent 线月 token 成本下降约 30%。通过重排、去重与 token 预算控制收敛上下文；这与 OCR-RAG 样本回放中的“输入上下文减少约 30%”是两个指标。

AST 校验解决 SQL 执行安全；检索误拒率下降来自检索架构调整，两者分开归因。

OCR-RAG · 多模态文档问答

文档资产治理 / 双图编排 / 页级强制溯源

企业生产项目
01业务问题
业务人员从扫描件、跨页表格与复杂版式文档中查找信息，人工定位慢。OCR 的错字、错数和表头丢失还会传递到答案，必须能回到原页复核。
02我负责的范围
2024.05–2026.03，在 NTT DATA 带 5 人技术线共同交付两条生产线；本项目于 2025.12 首次上线。负责双图架构、OCR 解析与切分、入库状态机及任务重试。
03一个关键技术取舍
把在线问答与离线入库拆成两张图，用带版本的文档中间结构隔离 OCR 与下游。否掉“一条链串完入库和问答”：两者的延迟与吞吐诉求不同，拆开后可独立恢复、演进，入库失败不阻断已入库文档的在线问答。
04结果与口径
P95 约 3.2s已入库文档的在线问答延迟，不含首次入库。

灰度期业务采纳率 约 70%。

样本回放中，通过重排、去重与 token 预算控制，输入上下文减少约 30%。

展开双图链路与页级溯源说明

离线入库

逐页 OCR → 带版本的中间结构（正文、页信息、元数据）→ 版式感知切分 → 索引。OCR 升级由中间结构隔离；入库状态与重试独立管理。

在线问答

问题处理 → Dense + BM25 混合检索与 RRF 融合 → 重排、去重与预算控制 → 带页级引用的回答。证据分数不足时确定性拒答；重排服务不可用时直接失败，不静默降级。

引用来自文档块的页信息，由系统生成，不让模型编页码。每个答案能定位到源 PDF 的具体页，支持审计复核；溯源并不替代 OCR 质量检查。

AI-SDLC · AI 原生研发流水线

Agent Harness / 证据与审批绑定 / 级联失效

独立自研 · 在运行
01业务问题
研发人员把编码交给模型后，仍要判断变更是否满足需求、证据是否对应当前代码。返工时沿用旧检查或旧审批，会让新代码带着上一版结论进入交付。
02我负责的范围
2026.04 至今，1 人独立完成架构、实现与自动化测试。自研并在运行的 AI 研发流水线，可现场演示，源码暂不公开。
03一个关键技术取舍
每阶段采用生成 → 确定性验证 → 裁决，否掉“一个大 Agent 自由循环调工具”。模型只提交候选；系统管理补丁、测试、证据与审批。退回重写时，下游检查、人审和 CI 结论级联失效，重新取证。
04结果与口径
10 阶段 · 201 条测试十阶段全部设有不依赖模型的确定性验收；10,424 行 Python 源码、201 条自动化测试仅说明实现规模（含控制台，统计于 2026.09.09）。
